# แนวคิด: การเพิ่ม database ในอนาคต

> **สถานะ:** ยังไม่ทำ — เก็บไว้เป็นแผน (ตัดสินใจเมื่อ 13 พ.ย. 2026)
> **กลุ่มผู้ใช้เป้าหมายตอนนี้:** คนทั่วไปที่เรียนด้วยตัวเอง
> **หลักการปัจจุบัน:** เข้าใช้ได้ทันที ไม่ต้อง login ไม่มี server/database — ความคืบหน้าอยู่ใน `localStorage`

## ควรเริ่มทำเมื่อไร

เพิ่ม database ก็ต่อเมื่อมีเหตุผลจากผู้ใช้จริง เช่น

- ผู้ใช้ขอให้ซิงก์ความคืบหน้าข้ามเครื่อง หรือบ่นว่าข้อมูลหาย
- มีคนแจ้งบ่อยว่าตัวตรวจลายมือตัดสินผิด และอยากเก็บตัวอย่างลายมือจริงมาปรับ
- ต้องการแจ้งเตือนรายวันเพื่อให้คนกลับมาฝึก
- เริ่มทำคันจิหรือคำศัพท์ที่มีเนื้อหาเยอะ จนอยากแก้เนื้อหาผ่านหลังบ้านโดยไม่ต้อง deploy ใหม่

## ลำดับเฟสที่วางไว้

### เฟส 0 — ยังไม่ต้องมี database (ทำได้เลยเมื่อพร้อม)

ฟีเจอร์ที่ช่วยให้คนกลับมาฝึกต่อเนื่อง เก็บใน `localStorage` ได้ทั้งหมด

- นับวันที่ฝึกต่อเนื่อง + ตั้งเป้ารายวัน
- หน้า “ถึงรอบทบทวนวันนี้” (spaced repetition — ต่อยอดจากระบบกล่องทบทวนที่มีอยู่แล้ว)
- กราฟพัฒนาการย้อนหลัง
- สำรอง/นำเข้าความคืบหน้าเป็นไฟล์ (ใช้แทนการซิงก์แบบง่าย)
- สถิติผู้เข้าชมด้วยบริการ analytics ภายนอก (เช่น Cloudflare Web Analytics)

### เฟส 1 — database แบบไม่ต้อง login

- ปุ่ม “แจ้งว่าตรวจลายมือผิด” พร้อมส่งตัวอย่างลายมือ **เฉพาะคนที่ยินยอม** → ใช้ปรับเกณฑ์ใน `src/features/writing/engine/`
- สถิติรวมแบบไม่ระบุตัวตน เช่น ตัวที่คนผิดบ่อย คู่ตัวที่สับสนกัน → นำมาปรับตัวหลอกในข้อสอบและเพิ่มคำแนะนำรายตัว

### เฟส 2 — login แบบไม่บังคับ (ยังมีโหมดใช้ทันทีเหมือนเดิม)

- ซิงก์ความคืบหน้าข้ามเครื่องอัตโนมัติ และข้อมูลไม่หายตอนล้างเบราว์เซอร์
- แจ้งเตือนรายวันผ่าน Web Push (“ถึงเวลาทบทวน 12 ตัว”)
- ชาเลนจ์รายสัปดาห์ / อันดับ (ใช้ชื่อเล่น)

### ไอเดียระยะไกล (ถ้ากลุ่มผู้ใช้เปลี่ยน)

- ห้องเรียนสำหรับครู/ติวเตอร์: สั่งงาน ดูความคืบหน้าและลายมือของนักเรียน
- ระบบหลังบ้านสำหรับเพิ่มคำศัพท์ ตัวอย่างคำ ไฟล์เสียง
- รุ่นพรีเมียม

## หลักการออกแบบ (ให้คงไว้เมื่อถึงเวลาทำ)

1. **localStorage ยังเป็นที่เก็บหลัก (offline-first)** — database เป็นแค่ที่สำรอง/ซิงก์ เว็บต้องใช้ออฟไลน์ได้เหมือนเดิม
2. **ไม่บังคับสมัคร** — ผู้ใช้ทั่วไปใช้ได้ครบ login มีไว้สำหรับคนที่อยากซิงก์
3. **เก็บข้อมูลให้น้อยที่สุด** — ไม่เก็บสิ่งที่ไม่ได้ใช้ และไม่ผูกข้อมูลลายมือกับตัวตน
4. **จุดเชื่อมในโค้ด** — ส่วนความคืบหน้าแยกอยู่ที่ `src/features/progress/progressStore.ts` และการตั้งค่าที่ `src/features/settings/settings.ts`
   (ทั้งคู่สร้างจาก `src/lib/persistentStore.ts`) เพิ่มชั้นซิงก์ที่นี่ได้โดยไม่ต้องแก้หน้าจอ

## ร่างข้อมูลที่ต้องเก็บ (คร่าวๆ)

| ตาราง | ใช้ในเฟส | ข้อมูล |
| --- | --- | --- |
| `handwriting_reports` | 1 | ชุดตัวอักษร, ตัวอักษร, จุดของเส้นที่เขียน, ผลที่ระบบตัดสิน, สิ่งที่ผู้ใช้คิดว่าถูก, เวลา (ไม่มีข้อมูลผู้ใช้) |
| `answer_events` | 1 | ตัวอักษร, รูปแบบคำถาม, ถูก/ผิด, ตัวที่เลือกผิด, เวลา (ไม่ระบุตัวตน) |
| `users` | 2 | id, วิธี login, วันที่สร้าง |
| `char_progress` | 2 | user_id, ชุดตัวอักษร, ตัวอักษร, กล่องทบทวน, ถูก, ผิด, คะแนนสูงสุด, `updated_at` |
| `push_subscriptions` | 2 | user_id, endpoint, เวลาแจ้งเตือนที่ต้องการ |

**การซิงก์:** รวมข้อมูลรายตัวอักษรโดยยึดแถวที่ `updated_at` ใหม่กว่า (ถ้าต้องแม่นยำขึ้น ค่อยเปลี่ยนไปเก็บเป็น event แล้วคำนวณใหม่)

## ตัวเลือกเทคโนโลยี

| ตัวเลือก | จุดเด่น | เหมาะเมื่อ |
| --- | --- | --- |
| **Supabase** (แนะนำ) | PostgreSQL + ระบบ login + Row Level Security, มี free tier, ใช้กับ React ง่าย | ค่าเริ่มต้นที่ดี |
| Cloudflare D1 + Workers | อยู่ที่เดียวกับเว็บ, เร็ว, free tier ใจดี | ถ้า deploy บน Cloudflare Pages |
| Firebase | มีระบบซิงก์ออฟไลน์ในตัว | ถ้าอยากได้ซิงก์สำเร็จรูปที่สุด |

## สิ่งที่ต้องเตรียมก่อนเปิดใช้

- นโยบายความเป็นส่วนตัวตาม **PDPA** + การขอความยินยอม (โดยเฉพาะตัวอย่างลายมือ และผู้ใช้ที่อาจเป็นเด็ก)
- ปุ่มลบบัญชี/ลบข้อมูลของตัวเอง
- กันสแปมและ rate limit สำหรับ endpoint ที่ไม่ต้อง login
- สำรองข้อมูล และประเมินค่าใช้จ่ายเมื่อเกิน free tier
